# log5.txt 分析报告

**背景**：用户反馈"已经冲出跑道了"，`log5.txt`是事后通过`log dump`取出的`/track.log.*`环形缓冲区内容，本次分析定位实际发生了什么、以及根本原因。

配置：`{"speed":16,...,"algo":0,"pid_kp":40,"pid_ki":0,"pid_kd":0,"file_log":true,...}`，即**BANGBANG算法**，`speed=16`，全程`print file on`处于开启状态。

本次分析的log段落是文件里最后一次`TRACK_ON`（segment 3，`#3178 TRACK_ON t=530441 algo=BANGBANG speed=16 turn_ratio=0.65 sharp_ratio=-0.40`）到log结束的这一段。

---

## 1. 事发时间线

| 时间(t=) | 事件 |
|---|---|
| 530441 | `TRACK_ON`，BANGBANG，speed=16 |
| 530442~532192 | `STRAIGHT`一路很稳，压线正常，持续约1.75秒 |
| 532573 | 第一次`LOST_R`，约500ms后重新找到线 |
| 532573~539665 | **此后再没有恢复过稳定跟踪**：`LOST_L`/`LOST_R`/`SHARP_L`/`SHARP_R`反复切换，每次找到线只维持几百毫秒又丢，持续约7秒 |
| 539665 | log在仍处于`LOST_R`状态时**戛然而止** |
| （紧接着） | 下一行是`ets Jul 29 2019 12:21:46`——ESP32开机bootloader横幅，**说明设备在这里发生了复位**，与"冲出跑道"的描述吻合（大概率是冲击导致接触不良/电流冲击触发复位） |

丢线期间传感器原始值（如`2544B 2246B 2201B 2521B 2454B`）均明显高于对应通道阈值（`[1546,1580,1422,1400,1500]`），确认是**真丢线**（车已偏出白线范围），不是阈值误判。

---

## 2. 关键证据：控制环速度异常下降

`sensor_debug.ino`新增的`LOOP`统计（`micros()`实测每圈耗时，每秒汇总一次）显示：

```
idle（未track on）                        ：约80000/s，avg 12~14us
track on，STRAIGHT稳定跟踪时（#3208）      ：12681/s，avg 78us   （已经比idle慢约6倍）
track on，进入丢线反复挣扎后（#3241起）    ：约300~420/s，avg 2300~3100us，个别max达218980us(219ms)
```

也就是说：
1. 只要`track on`+`print file on`同时开启，哪怕车跑得很稳，loop速度已经从idle的~80000Hz降到~12681Hz
2. 一旦车开始在丢线边缘反复挣扎，loop速度进一步暴跌到~300~400Hz，个别单圈耗时超过200ms

---

## 3. 根因分析

这一现象与`log-2.txt`/`log3.txt`已经验证过的结论一致：**flash文件log的flush操作本身要花费几十到两百多毫秒**（详见`print_module.cpp`的实现和2026-07-29的两轮修复记录）。

`track on`时`track_module.cpp`的调试log（`T`行）按`DEBUG_INTERVAL_MS=30`节流，即约33行/秒；加上`sensor_debug.ino`每200ms一次的传感器数据行（5行/秒），track on时合计约38行/秒，是idle时（约6行/秒）的6倍多。日志量越大，`LOG_BUF_CAPACITY=512`字节的缓冲区攒满的速度越快，触发flash flush的频率也越高（idle约1.5秒一次，track on时约0.27秒一次）。而每次flush耗时几十到两百多毫秒不等——**这段时间里整个loop()被阻塞，电机指令完全冻结，不会有任何转向修正**。

对一台正在过弯/处于丢线边缘、需要快速反应的小车来说，哪怕只冻结100~220ms，也足以让它冲出赛道有效范围。据此推断：**这次冲出跑道，根本原因大概率不是bang-bang算法或参数本身的问题，而是`print file on`这个诊断功能在实际跑动时，把控制环拖慢到了不安全的程度**，car在需要快速纠正的瞬间因为flush卡顿错过了修正时机，之后陷入持续丢线-找线的恶性循环，最终真的冲出赛道并导致设备复位。

**需要说明的局限性**：以上是基于`LOOP`统计数据和已验证的flash flush耗时机制做出的推断，具备较强的证据链（时间上吻合、机制上已经在idle场景验证过），但**并未做"关闭file log后跑同一段是否还会冲出去"的对照实验**，严格来说还不是100%排他性证明，建议按第4节的建议验证。

---

## 4. 建议

1. **正式测试/比赛时不要开`print file on`**，只在专门抓log排查问题的短时间调试session里开，跑真实赛道时关掉，避免这个副作用拖慢控制环
2. 如果需要保留"边跑边记log"的能力，可以把`LOG_BUF_CAPACITY`（当前512字节）调大，降低flush触发频率（代价是断电时可能丢一小段还没落盘的数据）
3. 对照实验：关闭`print file on`，用同样的`speed=16`/BANGBANG参数重新跑一次同一段赛道，确认是否还会在同样的位置丢线/冲出去——如果不再冲出去，就能实锤这次根因就是file log拖慢控制环，而不是bang-bang参数本身需要调整
4. 在此结论验证之前，不建议因为这次冲出跑道就去调`turn_ratio`/`sharp_ratio`等bang-bang参数，避免在错误的方向上调参
