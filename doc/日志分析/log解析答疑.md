## Q1：log19 第 25 行 CH3 已经亮了，为什么没直接执行转弯？是哪个参数影响的？

**看的这行**：`log19` line 25 → `E28 0C 4 98 98`
- `0C` = CH3+CH4 压白线（线到了右侧）
- `4` = **MEDIUM_R**（右转一档）
- L=98 R=98（左右轮几乎没差速）

### 结论先给
**它其实已经"执行转弯"了**——line 25 这一行的模式就是 MEDIUM_R，说明控制器**在这一瞬间就做出了右转决策**，一点没延迟。你觉得"没转"，是因为看到 L/R 还都是 98、没拉开差速。而"差速没立刻拉开"是 **`slew_rate`（PWM 变化速率限制）** 造成的。

### 关键：决策 与 执行 是两回事
1. **决策(选模式)**：每个 loop 都读传感器→选模式，**瞬时**。line 25 已经是 mode 4(MEDIUM_R)，证明决策没延迟。
2. **执行(下发PWM)**：每个模式有一对"目标 L/R"。但代码不把目标**一步到位**下发，而是经过 `slew_toward()` **限速逼近**——每毫秒最多变 `slew_rate/1000` 个单位。所以 PWM 是"爬"到目标的，切换那一瞬间还没爬到位。

### 具体算给你看（log19 参数）
参数：base=108(speed17)、medspeed=0.85、medium_ratio=0.65、minpwm=70、**slew_rate=5000**。

MEDIUM_R 的**目标** L/R（`track_module.cpp` 的 `medium_r` 分支）：
```
base_med = base × medspeed        = 108 × 0.85 = 91
外轮 L   = floor_fwd(base_med)     = 91          (>minpwm70, 不变)
内轮 R   = base_med × medium_ratio = 91 × 0.65  = 59
→ 目标 L=91, R=59   (左快右慢 = 右转)
```

而 `slew_rate=5000` → **5 单位/ms**。切换前是直行 108/108，切到 MEDIUM_R 后 PWM 从 108 往目标爬：

| 时刻 | 左轮 L(→91) | 右轮 R(→59) | 说明 |
|---|---|---|---|
| 切换瞬间(line25, ~爬了1步≈10单位) | 108→**98** | 108→**98** | 两轮都刚从108降10，还相等 |
| 约 +3ms 后 | 到 91(停) | 继续降 | 左轮到位 |
| 约 +10ms 后 | 91 | 到 **59** | 右轮到位，差速完全拉开=在转 |

- 左轮要降 17 单位 → 17÷5 ≈ **3.4ms** 到位；
- 右轮要降 49 单位 → 49÷5 ≈ **9.8ms** 到位。
- 所以**大约 10ms 内**这个右转就完全下发到位了。line 25 只是抓到了"刚起步第一步"的那一帧，所以显示 98/98。

> 顺带解释 line 25 两轮为何"相等(98/98)"：它们都从 108 出发、这一步都只动了同样的 ~10 单位，还没到各自不同的目标(91 vs 59)，再往后几毫秒右轮继续降、就分开了。log19 下一行 line 26 已经是 `81 49`(切到 SHARP_R)，差速就出来了。

### 到底哪个参数影响？
- **直接原因 = `slew_rate`**：它限制 PWM 每秒最多变多少。值越大→越快到位(几乎瞬时)；值越小→爬得越慢(就是 log13/14 里 slew=600 造成 ~200ms 滞后、"往外扭"的元凶，见 `log15分析.md` 第八节)。log19 用的是 5000，已经很快，10ms 就到位。
- **决定"转多狠"(目标值)的参数**（不是"快慢"，是"幅度"）：
  - `medspeed`（MEDIUM 档整体降速系数）→ 定 base_med；
  - `medium_ratio`（内轮减速比例）→ 定内轮目标；
  - `minpwm`（外轮最小 PWM 地板）→ 防外轮被降到堵转。
  这三者决定 MEDIUM_R 的目标是 L91/R59（一个**温和**的右转，内轮只是减速、不反转）。

### 一句话
line 25 **决策上已经在右转**了；看到 98/98 是因为 `slew_rate` 让 PWM 分几毫秒"爬"到转弯目标(L91/R59)，抓到的是起步第一帧。想让转弯下发更快→调大 `slew_rate`；想让转弯更狠→调 `medspeed`/`medium_ratio`（那是幅度，不是快慢）。

## Q2：CH3=1 不是"车往右偏"吗？为什么还往右调节？（方向理解 + 10ms 是否算延迟）

延续 Q1。两个疑问：① slew 说"10ms 就到位"，可 10ms 也是时间啊；② CH3 亮了应该是小车往右偏，为什么还往右转？

### ① "10ms 也是时间" —— 对，但可以忽略
- 小车速度约 0.3~0.8 m/s，**10ms 只走 3~8mm**，还不到一个传感器间距。
- 而过弯、丢线是**几百毫秒**尺度的事。这 10ms 是零头，**不是小车往外跑的原因**（真正原因见 ③）。

### ② ⭐核心：**亮的传感器 = 线在哪，不是车在哪**
最容易绕反的地方：**某个 CH 亮(=白=压线)，表示"线"落在那个位置，不代表"车"在那个位置。**

从车头往下看这排传感器（物理左→右）：
```
  CH8 CH7 CH6 CH5 | CH4 CH3 CH2 CH1
  左 ............中心............ 右

线压在 CH3:
  CH8 CH7 CH6 CH5 CH4 CH3 CH2 CH1
                       ●(线)
        └── 线在中心的右边 ──┘
```
- 线跑到 CH3(右侧) → **线在车的右边** → 等价于**车相对线偏到了左边**（或前方轨道往右拐）。
- 要让线回到中心(CH4/CH5)，就得**让车往右靠 → 右转**。
- 右转让车往右走，线(固定不动)在传感器视野里相对**往左移**，从 CH3 挪回中心。✓

**所以右转是对的。** 若按直觉往左转，线会更往右跑到 CH2、CH1，直接冲出去——那才是错的。

> 记忆口诀：**线偏哪边，就往哪边追**。线在右(CH3)→右转追它；线在左(CH6)→左转追它。
> 也和 PID 的 err 符号一致：本工程约定 err>0=线偏右→右修正(左轮加速/右轮减速)。

### ③ 方向对了为什么还往外跑？
方向没错，是**力度/时机输给了速度**：
- 进弯太快，线从 CH3→CH2→CH1→丢 是在几十~几百毫秒内快速扫向边缘的；
- MEDIUM_R 是**温和右转**(内轮只减速到 59、不反转)，追不上线扫向边缘的速度；
- 等升级到 SHARP/HAIRPIN 想使劲追，线已到边缘甚至丢了(log19 line27 就 HAIRPIN_R、line28 就 LOST_R)。

即"**恒速冲进弯、来不及转就冲到最外侧丢线**"(见 `log17分析.md`)。是"追得不够快/不够狠"，**不是追错方向**；根子还是**车速降不下来**(电机死区)。

### 一句话
亮的 CH = 线的位置(不是车的位置)；**线偏哪追哪**，CH3(右)→右转是对的。10ms 可忽略。往外跑是"追不上线扫向边缘的速度"，不是方向错。

## Q3：slew_rate 到底是什么？代码里复杂吗？怎么调？

### 代码里不复杂——就是一个"限速器"
`track_module.cpp` 的 `slew_toward()`，核心就三步：
```c
dt       = 距上次调用过了多少秒
max_step = _slew_rate * dt          // 这一步最多允许变多少个PWM单位
// 对每个轮子:
diff = 目标值 - 当前值               // 还差多少
把 diff 限制在 ±max_step 之内        // 一步最多迈这么多
当前值 += diff                      // 朝目标挪一小步 -> 下发
```
没有滤波公式、没有状态机，**就是"每次朝目标挪一小步，步子大小有上限"**。

### 一句话本质
- 各模式先算出**目标 L/R**（如 MEDIUM_R 目标 L91/R59）。
- **slew_rate 决定"多快爬到这个目标"**：限制**下发电机的 PWM 每秒最多变多少个单位**。
- 目标=去哪；slew_rate=每秒最多走多远。
- 比喻：像音量旋钮想拧到 30 格(目标)，但**每秒最多拧 N 格**。N 大=一下拧到；N 小=慢慢拧。

### 数值直觉（PWM 变 128 单位要多久，满量程 0~255）
| slew_rate | 每毫秒变 | 变128要 | 感觉 |
|---|---|---|---|
| 300 | 0.3 | 427ms | 很肉，严重滞后(log13/14 往外扭元凶) |
| 600 | 0.6 | 213ms | 偏慢，明显滞后 |
| 1000 | 1.0 | 128ms | 中等 |
| 2000 | 2.0 | 64ms | 较快 |
| **5000** | 5.0 | 26ms | 几乎不限速(当前用) |
| 50000 | 50 | ~3ms | 等于没有 slew，瞬间到位 |

### 怎么调
- **命令**：`slewrate N`（如 `slewrate 2000`），运行时即时生效；`save` 固化。
- **看症状往哪调**：
  - 车**高频抖动 / 在边界左右硬来回打** → **调小**(多点平滑)。
  - 车**反应慢、修正跟不上、冲过头** → **调大**(去滞后)。
- 一次只改这一个，跑一趟对比 log。

### 对本车的建议
- 现在 `slew_rate=5000` 已接近"没有 slew"，实测配合好(log15/16 直线稳)，**一般不用回头压它**。
- 之前压到 600 反而坏事(滞后→往外扭)。方向应是**保持 slew 高**，平滑交给别的手段(柔化 ratio / 迟滞 / PID，见 Q2 及 `log17分析.md`)。
- 记忆：**slew 管"快慢/滞后"，ratio 管"转多狠"**。本车缺的是"转得够快够狠"，不是"太猛要压"，所以 slew 保持大。

## Q4：CH4+CH5 只有两个亮，明明是正对中心，为什么被判成 CROSS(十字)？

**结论**：这是当前"十字检测"写得**太松**导致的误判。CH4+CH5 是正对中心，不是十字。

### 为什么会误判
代码里十字是这样判的(`track_module.cpp`)：
```c
// 左半(CH5..CH8)有白 且 右半(CH1..CH4)有白 → cross
for (i=0..3) if(is_white[i]) right_any=true;   // CH1 CH2 CH3 CH4
for (i=4..7) if(is_white[i]) left_any=true;    // CH5 CH6 CH7 CH8
bool cross = left_any && right_any;
```
分界线正好切在 **CH4 与 CH5 之间**：CH4 属"右半"、CH5 属"左半"。所以最居中的 **CH4+CH5 恰好一边一个 → 被判成"左右都压线=十字"**。条件太宽，不是真有十字。

### 实际影响
- **多数时候没坏事**：CROSS 模式就是"直行 108/108 不转向"，正对中心本来也该直行，所以**行为碰巧对，只是标签错**(log 里看到 mode 9 其实是直行，容易看糊涂)。
- **有时会吞掉该做的小修正**：只要线宽到跨过中线就触发。如线压 **CH3+CH4+CH5**(中心略偏右、该小右转)也满足"右半有 CH3/CH4 + 左半有 CH5"→ 判 CROSS → 直行**不修正**。这是真副作用。

### 真正的十字该怎么判
真十字/横杠**横穿整个赛道**，会让**两侧最外**的传感器都亮。判据应是"线跨得很宽"，不是"随便左右各一个"。两种干净写法：

① 看两侧最外（推荐，最稳）：
```c
bool far_left  = is_white[6] || is_white[7];  // CH7/CH8
bool far_right = is_white[0] || is_white[1];  // CH1/CH2
bool cross = far_left && far_right;           // 两远端都亮才算十字
```
CH4+CH5、CH3+CH4+CH5 都不会误判；只有真横杠(两端都压)才触发。

② 看白的数量：
```c
bool cross = (n_white >= 5);   // 至少5路同时白 = 横杠穿过
```

改完后 CH4/CH5(一个或两个)回落到 **STRAIGHT(mode 0)**：既直行、标签也对，线略偏时也能正常触发小修正。

> 状态：**已按方案①改代码**（2026-08-09）。`track_update()` 里 cross 改为
> `far_left(CH7||CH8) && far_right(CH1||CH2)`。CH4+CH5 现在回落到 STRAIGHT(mode 0)。待编译/实车验证。

## Q5：pattern 从 CH5 直接跳到 CH3+CH4，中间隔了 204ms，为什么没记"CH5→CH4"那条？

**看的两行**（log23）：
```
line68  E24  10 0 57 108    CH5,      mode 0 STRAIGHT
line69  E204 0C 4 97 63    CH3+CH4,  mode 4 MEDIUM_R  (dt=204ms)
```

**结论**：log **只在"档位(modeCode)变化"时记一行**，不是每次传感器 pattern 变化都记（`../设计/LOG精简方案.md`：事件触发+心跳，省内存缓冲）。

代码逻辑：
```c
mode_changed  = (本次mode != 上次mode);
heartbeat_due = 没变 且 距上条记录 >= 500ms;
if (mode_changed || heartbeat_due) 才写一行;
```

**关键：CH5、CH4+CH5、CH4 全是同一个档 = STRAIGHT(0)**（中心两路不触发转向；CH4+CH5 在新 cross 逻辑下也不是 cross）。所以那 204ms 里线从 CH5 一路飘到 CH4，**档位一直是 0、没变 → 一行都不记**；直到线飘到 **CH3** 才第一次触发 MEDIUM_R(4)，这才记 line69。

```
CH5 → CH4+CH5 → CH4 → CH4+CH3
 └───── 全是 mode 0 (STRAIGHT) ─────┘   ← 只记了开头 line68
                                 └ CH3亮→mode4 → 记 line69
```
- line69 的 dt=204 = "档位停在 STRAIGHT"的持续时长；
- 204ms < 500ms 心跳间隔，中间也没心跳补一条；
- line69 的 patHex `0C` 只是"变成 MEDIUM_R 那一瞬间"的 pattern 快照，中间同档 pattern（CH4、CH4+CH5）没被采到。

### 要记住的点
**log 里的 patHex 不是"传感器随时间的完整轨迹"**，它只在**档位切换的瞬间**采样一次。长直行段（都是 mode 0）里线在中心几路间怎么飘是看不到的——档位没变就不记。要连续位置得靠"档位边界"推，或改成固定周期采样（log 会大很多）。

## Q6：MEDIUM_R 之后 134ms 直接变 LOST，没经过 SHARP/XSHARP，是 134ms 都没信号吗？

**看的这段**（log23）：
```
line69  E204 0C 4 97 63    CH3+CH4, MEDIUM_R
line70  E134 00 B 108 -37  全黑(00), LOST_R
line71  E2   02 6 108 -43  CH2,     SHARP_R    ← 只隔 2ms
line72  E389 04 4 97 57    CH3,     MEDIUM_R
```

### 纠两个误读
**① 134ms 不是"没信号"，是 MEDIUM_R 保持了 134ms（这段一直有 CH3 正常信号）。**
dt="距上一次切换"，写在**新状态那一行**。line70 的 `134` = 它前面 line69 的 MEDIUM_R **持续了 134ms**；这 134ms 档位一直是 MEDIUM_R、信号正常。LOST 是 134ms **末尾**才发生、从 line70 开始。

**② 没有跳过 SHARP。line71 就是 SHARP_R(CH2)，在 LOST 之后仅 2ms 出现。**
真实微观顺序：
```
CH3(MEDIUM_R, 134ms) → 全黑(LOST_R, 仅2ms) → CH2(SHARP_R)
```
line70 的 LOST 只持续 **2ms**（line71 的 dt=2）——不是"变 LOST 回不来"，而是**闪了 2ms 全黑，CH2 就接上了**。

### 那 2ms 全黑=相邻两路之间的"缝"
线从 CH3 挪到 CH2 途中，约 2ms 落在 **CH3 与 CH2 中间的缝**：那一瞬间**既没盖住 CH3、也没盖住 CH2**，两路都没过白阈值 → 8 路全黑 → 判 LOST_R 2ms。再挪一点盖上 CH2 就恢复 SHARP_R。
这是**"细线 + 离散传感器"的正常现象**：线比传感器间距窄时，相邻两路交接会有极短"谁都没压实"的瞬间。代码里 LOST 不立刻停、而是"延续上次方向找线 + 1500ms 超时"，正是为了**桥接这几毫秒的相邻缝隙**。

### 为什么没有 XSHARP(CH1/发卡)？
线只往右到 **CH2 就回来了**（line72 又变回 CH3/MEDIUM_R），**没走到最右的 CH1**，自然没有 HAIRPIN_R。它在 CH3↔CH2 之间来回，没到极端边缘。

### 一句话
`134` 是 MEDIUM_R 的**持续时长**（信号正常），不是无信号；LOST 只是末尾 **2ms 的全黑闪断**（线落在 CH3/CH2 之间的缝），紧接着 line71 就是 SHARP_R；没到 CH1 所以没有发卡档。
