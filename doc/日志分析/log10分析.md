# log10.txt 分析报告

**背景**：用户实车**完整跑完了一圈**（bang-bang本身能把车带完一整圈，没有中途失控），`track on`后没有干预，跑完之后**手动把车抬起来按了track off**（结尾那段`LOST_STOP`是车被拿离地面/线之后触发的丢线超时，不是车自己在跑道上冲出去丢线的——这点之前的版本理解错了，已更正）。这是新版内存log（不限时长、按剩余空间截止）第一次在真实长时间跑动场景下的完整数据，也是`8路+4级差速bang-bang`在"摆动幅度太大"这个最初问题上第一份可供定量分析的实车证据。**关键结论不变但严重程度要修正**：这次的问题是"跑完全程但摇摆明显"，不是"跑不完/会失控"——跟后面`log-alg0-1分析.md`里slewrate调到300之后出现的真实发散性失控（19秒内3次丢线停车）相比，严重程度是两个量级，不能混为一谈。

配置（`PARAMS`行）：`algo=BANGBANG speed=17 turn_ratio=0.65 medium_ratio=0.35 sharp_ratio=-0.40 xsharp_ratio=-0.60 slew_rate=5000.0`。

时间线：`TRACK_ON t=31851` → `TRACK_OFF t=142017`，`elapsed=110166ms`（约110秒）、`duration=110014ms`、`lines=898`（830条事件行E + 66条心跳行H + TRACK_ON/PARAMS两条标记）。结尾连续近40条`LOST_STOP`心跳，是车被抬起来之后传感器读不到线触发的丢线超时停车，不代表车在跑道上自己冲出去了——这一整圈期间，car是持续在跑道上完成了全程的。

---

## 1. 核心发现：`slewrate`被设成5000，等于没开PWM平滑

`PARAMS`行里`slew_rate=5000.0`——这个数字比项目一直以来的默认值`800`（`SLEW_RATE_DEFAULT`）还要高出6倍多，比最初诊断"摆动幅度太大"那次建议的"降到300~500试试"反方向调了10倍。

算一下这个数字的实际含义：PWM量程是±255（满摆幅510），限速`5000`单位/秒意味着**从一个极端摆到另一个极端只需要约102毫秒**。而下面第2节能看到，本次实测大量档位切换的间隔（`dt`）本身就短至个位数到几十毫秒——也就是说绝大多数切换发生得比"PWM摆满一圈所需的102ms"还快，slew限速在这些切换之间几乎不起任何平滑作用，实际效果跟完全不限速（`SLEW_RATE_DEFAULT`引入之前的老版本）没有本质区别。

项目历史上这个参数是专门为了治"硬跳变导致左右摇摆剧烈"加的，而且用户确认过有效（见`设计说明.md`决策记录）。这次`slew_rate=5000`很可能是之前调试/试参数时改上去、忘了改回来——**这是本次摆动问题最值得优先怀疑的一处配置**，不是算法逻辑本身的锅。

---

## 2. 数据证据：档位切换频率+两两切换统计

对830条事件行（`E`）的`dt`（距上次真正切换的间隔）做了分布统计：

| dt区间 | 条数 | 占比 |
|---|---|---|
| ≤10ms | 198 | 24% |
| 11~50ms | 172 | 21% |
| 51~100ms | 176 | 21% |
| 101~300ms | 223 | 27% |
| >300ms | 61 | 7% |

**近四分之一的档位切换发生在10ms以内**——档位刚切过去，不到10毫秒又切回来（或切到相邻档），这正是"摆动"在数据上的直接体现。

进一步看具体是哪些档位之间在来回跳（`modeCode`两两转换次数，全部830次里排前几名）：

| 转换 | 次数 | 含义 |
|---|---|---|
| `2>9` / `9>2` | 77+73=150 | RIGHT缓转 ↔ CROSS（十字/宽线判定） |
| `4>2` / `2>4` | 67+66=133 | MEDIUM_R中转 ↔ RIGHT缓转（相邻档） |
| `2>B` / `B>2` | 62+21=83 | RIGHT缓转 ↔ LOST_R丢线 |
| `3>A` / `A>2` | 50+44=94 | MEDIUM_L中转 ↔ LOST_L / RIGHT缓转 |
| `5>3` / `3>5` | 40+48=88 | SHARP_L急转 ↔ MEDIUM_L中转（相邻档） |
| `7>5` / `5>7` | 38+40=78 | HAIRPIN_L发卡 ↔ SHARP_L急转（相邻档） |
| `6>4` / `4>6` | 29+29=58 | SHARP_R急转 ↔ MEDIUM_R中转（相邻档） |

只看≤10ms的"快速来回"，排名结构完全一致，`9>2`（45次）、`2>4`/`4>2`（24+21=45次）、`2>B`/`B>2`（20+17=37次）是最密集的三对。

**每一级相邻档位之间（发卡↔急转、急转↔中转、中转↔缓转/丢线）都在互相"串门"**，不是单独某一个弯道的孤立问题，而是全程系统性的——这跟"slew限速没生效，档位一切换PWM就硬跳到位，车身跟着硬来回打"这个机制完全吻合：车压过传感器边界一点点，PWM立刻跳到新档的目标值，车身来不及跟手就已经反向冲过了边界，于是立刻又跳回上一档，如此反复。

另外`RIGHT缓转↔CROSS`这一对占比最高（150次，约占全部切换的18%），比例明显偏高——`CROSS`按设计只应该在真正的十字路口/宽线才触发，一圈里出现这么多次，值得怀疑是不是在缓转边界附近，左右两组传感器偶尔同时压到线导致误判成"CROSS"，跟阈值标定或传感器间距有关，不完全是纯粹的转向力度问题（见第4节建议）。

## 3. 差速比例本身应用正确，不是这次的问题

抽查了几组`L/R`实测值，跟`PARAMS`里的配置换算完全吻合（`base`≈108，对应`speed=17`）：

- MEDIUM_R：`L=108 R=37`，算出来`108×0.35=37.8`，对得上`medium_ratio=0.35`
- LOST_L/LOST_R：`L或R=-43`，算出来`108×(-0.40)=-43.2`，对得上`sharp_ratio=-0.40`
- HAIRPIN：`L或R=-64`，算出来`108×(-0.60)=-64.8`，对得上`xsharp_ratio=-0.60`

说明4级差速的比例计算、代码逻辑本身没有问题，这次"摆动"是**切换太快+PWM跳变太硬**共同造成的现场表现，不是差速比例算错了。

---

## 4. 下一步调参建议（按优先级）

1. **先把`slewrate`降下来，这是本次最大的嫌疑**：`slewrate 300`（比默认800更保守）测一次，跟这次log10同一段路对比`log dump`里≤10ms快速切换的占比和`9>2`/`2>4`这几对的次数是否明显下降。如果好转很多，说明这次摆动主因就是slew没生效，把它调回合理区间（300~800之间找手感）即可，其他参数可以先不动。
2. **如果降slewrate后仍有明显摆动，再看`mediumratio`**：`4>2`/`2>4`（缓转↔中转）和`6>4`/`4>6`（中转↔急转）这两组占比也很高，说明"缓转→中转"这条边界本身可能也偏敏感，可以尝试把`mediumratio`从35调到45~50，让中转档修正力度更接近缓转，减小相邻档之间的PWM落差。
3. **单独排查`CROSS`误触发**：`RIGHT缓转↔CROSS`这一对占比最高，建议`print on`之后专门跑一段"正常缓转但确定不是十字路口"的路段，实时看`patHex`位图，确认是不是左右两组传感器在缓转边界附近偶尔同时压线——如果是，需要回头看CH1~CH4（物理右半组）的`threshold`标定是否偏松，不是转向参数的问题。
4. **每次只改一个参数、测一趟、对比这份log的统计口径**（≤10ms占比、相邻档转换次数），不要一次改多个，不然分不清是哪个参数起的作用——这份log10的统计数字可以直接当基线用。
