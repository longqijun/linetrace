# log6.txt 分析报告

**背景**：用户反馈"这个是PID调节的，基本上没有办法使用"。`log6.txt`是事后通过`log dump`取出的`/track.log.*`环形缓冲区内容。

配置：`algo=PID`，`speed=16`，`kp=40.00, ki=0.00, kd=0.00`（即2026-07-29重写后的固定周期+微分低通滤波实现，本次Kd=0相当于纯P），全程`print file on`处于开启状态。

log文件里segment 0/3是更早一次bang-bang测试（`log5.txt`分析过的那次冲出跑道）残留在环形缓冲区里还没被覆盖的旧数据，与本次无关。本次分析的是**segment 1开头的`TRACK_ON t=914 algo=PID`**到该次track彻底停止为止的这一段（跨segment 1和segment 2）。

---

## 1. 事发时间线

| 时间(t=) | 事件 |
|---|---|
| 914 | `TRACK_ON`，PID，speed=16，kp=40/ki=0/kd=0 |
| 914~约31800（约31秒） | 反复在"PID正常跟踪"和`LOST_L`/`LOST_R`之间切换，从未连续稳定跟踪超过1~2秒 |
| ≈33301 | 丢线持续超过1.5秒（`LOST_TIMEOUT_MS`），触发`LOST_STOP`，电机彻底停转（`L:0 R:0`） |
| 33301 ~ 46592（至少又过13秒） | **车一直停在原地，再未恢复**，直到用户手动`log dump`取出log |

全程没有出现`TRACK_OFF`标记，说明这次是车自己因丢线超时停下来的，不是手动停止的。

---

## 2. PID计算本身验证正确

从数据能直接验证重写后的PID逻辑算得对：

```
E:+0.25 → L:112 R: 92  （差速+10 = 40×0.25）
E:+0.50 → L:122 R: 82  （差速+20 = 40×0.50）
E:+0.75 → L:132 R: 72  （差速+30 = 40×0.75）
E:+1.00 → L:142 R: 62  （差速+40 = 40×1.00）
```

四档误差（±0.25/0.50/0.75/1.00）对应的差速精确等于`Kp×error`，跟`Kp=40`完全吻合。**2026-07-29的固定周期+微分低通滤波重写没有引入计算错误**，本次"基本没法用"不是PID公式本身算错了，是别的原因。

---

## 3. 根因：两个更早就点过名的老问题在PID模式下同样发作

### 3.1 转向权威不足（`log4-分析报告.md`已指出）

`Kp=40`打满误差时修正量只有±40，仅占base(102)的~39%。本次`speed=16`跟`log4`测试的低速档接近，再次印证：车转向力度不够，冲过线之后修正跟不上，直接丢线。

### 3.2 `print file on`拖慢控制环（`log5分析.md`已验证的同一机制）

`LOOP`统计跟`log5`（bang-bang冲出跑道那次）几乎一模一样的病态数值：

```
idle应有水平：约80000/s，avg 12~14us
本次PID实测 ：约300~400/s，avg 2300~3300us，个别单圈max达226602us(227ms)
```

同样是`print file on`开启后，flash flush期间整个loop()被阻塞、电机指令冻结这个已确认机制（详见`log5分析.md`第2、3节），在PID模式下同样发作，程度几乎一致。

### 3.3 两者叠加

本来`Kp=40`转向力度就偏弱，再叠加flush造成的100~200ms周期性控制冻结，车基本没有机会稳定跟线，最终连续丢线超过1.5秒触发`LOST_STOP`，彻底停摆，且没有任何机制能让它自己恢复（`LOST_STOP`之后除非车身重新压到线上或手动`track off`/`track on`，否则会一直停在原地）。

---

## 4. 建议

1. 先关掉`print file on`，同样`Kp=40/Ki=0/Kd=0`跑一次，看看丢线频率是否明显下降——如果好转很多，说明flash log是主因（跟`log5分析.md`建议的对照实验是同一个）
2. 不论上一步结果如何，都建议把`Kp`加大到100+（`pid kp 100`）——这是`log4-分析报告.md`最早给出、至今还没有在重写后的PID实现上验证过的建议
3. 两步都做，且分开测试（不要同时改两个变量），才能确认这次"没法用"具体是哪个因素占主导，还是两个因素叠加
