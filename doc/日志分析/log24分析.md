# log24 分析（lograte=10ms 首测：功能正常，但暴露 loop 周期性卡顿）

> 背景：实现 `lograte`（内存日志采样周期）后首次用 **10ms** 抓的 log。目的：确认 10ms 采样是否正常、有无异常。
> 配置：bb_fast 档，speed=17，`lograte=10`，其余同 log23（激进、弯道不降速）。

## 一、功能确认：10ms 采样正常 ✅
- PARAMS 里 `lograte=10` 已记录。
- 心跳行现在是 `H10`（每 10ms 一条）。
- 跑 ~67.6 秒 / **6633 行全程录下没溢出**（duration≈elapsed），说明缓冲扛得住整趟（约 145KB 用量）。
- H 的 dt 分布：**10ms×5746、11ms×101**——绝大多数正好 10-11ms（11 是 loop ~1ms 粒度的正常抖动）。**采样机制本身工作正常。**

## 二、⚠️ 异常：约 36 处 H 间隔达 45~211ms（本该 10ms），最大 211ms
H 的 dt 里混着一批大值：`45ms×1, 54~77ms×约30, 106, 114, 196, 203, 211ms 各1`。即**有 ~36 次，两条连续记录之间隔了 50~211ms，而不是 10ms**。

### 这是真·loop 卡顿，不是日志 bug
- 两条**连续行号**之间（如 line230 `H10` → line231 `H77`）本该有 6~7 条 10ms 心跳，却一条都没有 → 说明那 ~67ms 里 **loop 根本没执行到记录代码**。
- 这些大间隔在**各种状态都出现**——包括**直行(STRAIGHT)**时（line922 H71、line3589 H211）。直行时档位不变、没有"事件洪水"，却照样卡 → **与车在做什么无关，是外部原因周期性阻塞了 Arduino loop。**
- 发生频率：平均**约每 1~2 秒一次**（不严格周期），最大一次 **211ms**，另有几次 >100ms。

### 影响（为什么值得重视）
卡顿期间**整个控制回路冻结**：不读传感器、不重算、不更新电机。车**带着上一刻的 PWM 盲跑 50~211ms**。以当前车速，200ms 能走不少距离——足以在弯道冲过头/把线甩丢。**这很可能是控制不稳的一个隐藏推手**，只是以前用 500ms 心跳时被完全掩盖（一次 200ms 卡顿藏在两条心跳之间根本看不见），10ms 采样才把它照出来。

### 可能原因（待排查）
- **后台任务周期性抢占 loop**——最可疑是 **WiFi/系统任务**（ESP32 上 Arduino loopTask 与系统任务共核；WiFi 活动会周期性阻塞几十 ms）。仓库里有 `WIFI_PLAN.md`，需确认 **WiFi 当前是否开着/在扫描/连接**。
- 排查手段：① 确认并（测试时）关掉 WiFi；② 在 loop 里加"本次 loop 耗时"监测，把 dt>20ms 的记下来，定位是哪段代码/任务在阻塞。

## 三、次要观察
- **停车后仍每 10ms 记 `00 C`**：结尾有 251 条 `H10 00 C 0 0`（≈2.5 秒停车状态被反复采样），白占缓冲。可考虑 **LOST_STOP 后停止采样**（省缓冲、也让 dump 更干净）。
- 运行结果本身无新意：LOST 占比 **20.9%**，~68s（~7 圈）后 LOST_STOP，和 log21/23 一样是"激进参数、没裕量、靠运气"（见 `log21-22分析.md`）。cross 修复继续有效（CROSS 仅 1 次）。

## 四、结论
1. **`lograte=10` 功能正常**：采样密度、时间戳、整趟不溢出都 OK，PARAMS/config 都带上了 lograte。
2. **暴露出真问题：loop 周期性卡顿（50~211ms，约每 1~2 秒一次）**，卡顿期间控制盲跑。**建议优先排查**（先查 WiFi，再加 loop 耗时监测）——这比继续调巡线参数更值得先解决，因为它会让任何参数调优的结果都不稳定/不可复现。
3. 次要：停车后停止采样。
