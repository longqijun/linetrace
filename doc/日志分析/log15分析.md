# log15 数据分析报告（slew=5000，直线不丢）

> 背景：把 `slew_rate` 从 600 提到 **5000** 后重跑直线，**直线不再丢线**。后半段 pattern 变 `FF`（8 路全白）是轨道太短、跑到头没线了冲出去，**不是 bug**，只看前面。
> 本次参数（相对 log14 的改动）：
> - `slew_rate` 600 → **5000**（软件限速几乎放开）
> - `medium_ratio` 0.35 → **0.65**（一档更缓，内轮 ~70 而非 37）
> - `sharp_ratio` -0.40 → **-0.20**（反转更弱）
> - `xsharp_ratio` -0.60（不变），speed 17（不变）

## 一、结论先行：这次是成功的一步

| 指标 | log13 | log14 | **log15** |
|---|---|---|---|
| 起步干净直行时长 | 0（从不直行） | ~1.3s | **~3.0s** |
| 直线段是否丢线 | 3s 就丢失停车 | 漂出去丢线 | **不丢，反复自动回中心** |
| 振荡性质 | 发散 | 大幅极限环 | **有界小幅蛇形，收敛回中心** |

**关键判定**：这等于把"机械延迟排查文档"里的**实验 A（放开 slew 看过冲是否还在）**做了——放开 slew 后直线就不丢了、过冲大幅收敛。**说明之前"往外扭"的主因是软件延迟（slew=600），机械延迟不是主导因素。** 机械延迟就算存在，也不是当前瓶颈。

## 二、前 ~3 秒：干净直行 108/108

| 行 | pattern | 模式 | L/R | 该状态持续 |
|---|---|---|---|---|
| 13–16 | `08`(CH4) | 0 STRAIGHT | 108/108 | ~1.6s |
| 17 | `48`(CH7+CH4) | 9 CROSS 直穿 | 108/108 | 6ms 一闪 |
| 18–20 | `08`(CH4) | 0 STRAIGHT | 108/108 | ~1.2s |
| 21 | `18`(CH4+CH5) | 9 CROSS 直穿 | 108/108 | — |
| 22 | `10`(CH5) | 0 STRAIGHT | 108/108 | 到 t≈3.08s |

累计 **~3.08 秒**都是中心两路、左右轮满速 108/108 笔直向前，第一次真正转向修正才在 t≈3.08s（行 23）出现。比 log14 的 1.3s、log13 的 0 有质的提升。

## 三、~3s 之后：有界小幅蛇形（不再发散，能回中心）

从 t≈3.08s 起进入轻微蛇形，典型节奏是"漂到一侧边缘→修正→回中心→漂到另一侧"，但**每次都能拉回中心 108/108**，不再像 log14 一路发散到 LOST_STOP：

```
左漂(行23–34, CH7/CH6/LOST交替) → 回中心直行(行35–38, 108/108)
→ 右漂(行39–41, CH4/CH3) → 回中心(行42–45, 108/108)
→ 左漂(行46–57, 到CH8发卡) → 回中心(行57–59)
→ 右漂(行60–64) → 回中心(行65–66) → 左漂(行67–71) → 轨道到头
```

- 蛇形周期约 1~1.5s，幅度会碰到边缘传感器（CH6/CH7 偶尔 CH8），但都能恢复。
- 边缘偶尔仍触发发卡反转（行 51 `C0` mode7 -31/70、行 52 `40` mode5 -54/70），还有一点过冲，但已能收回。

## 四、轨道到头（无效数据，非 bug）

行 71 pattern `F8`（CH8~CH4 五路白）、行 72–74 `FF`（8 路全白）→ 传感器阵列整片压在白区，说明**车已冲出赛道尽头的黑线、进入开阔白面**。之后的 `E1851`、LOST_R、两轮 LOST_STOP（行 75–91）都是轨道没线之后的行为，**按用户说明属轨道太短，不计入分析**。

## 五、剩余问题与下一步

改善很大，但直线仍有**小幅蛇形**，没有稳稳压死中线。可能来源：

1. **中心死区偏宽**：CH4/CH5 之间不做任何修正，车在死区里攒了一点横向速度，等冲到 CH6/CH3 才修正，回摆时又冲过中心 → 典型死区极限环。
2. **残余过冲**：边缘偶尔还用发卡反转，仍有一点冲过头。
3. **可能的轻微左偏**：三次里第一次漂又是往左（行 23 先出 CH7），`传动比/左右轮不一致`的怀疑仍值得留意（见 `调试记录.md` 方向 2），但已属次要。

**建议下一步（择一试）：**
- **A. 微调收窄蛇形**：`sharpratio`/`xsharpratio` 再往 0 收（边缘也尽量不反转）；或把 `medium_ratio` 再调，找"能拉回又不过冲"的点。speed 可试降到 14 给更多余量。
- **B. 治本上 PID**：直线段换 PID（kp=40/kd=5 已配好），连续按偏差修正、没有死区、没有档位硬跳变，最有希望把蛇形压成近乎笔直。既然 slew 已放开、软件延迟不再是瓶颈，现在是试 PID 的好时机。
- **C. 验证左右轮**：按方向 2 实测左右轮同 PWM 转速，若有固定偏差加平衡补偿，把"直行"先做到零偏。

## 六、一句话总结

放开 slew（600→5000）+ 软化档位后，**直线从"漂出去丢线"变成"3 秒干净直行 + 有界蛇形不丢线"**，并顺带证明了主因是软件延迟而非机械延迟。剩下的小蛇形，建议直接试 PID 收尾。

## 七、附：能否从 log 里判断"电机/轮子反应慢"？

**直接结论：不能直接证明，只能给一个"总回路延迟"的上界。**

### 1. 根本限制：log 里没有轮子实际转速
日志每行的 `L/R` 是**下发给电机的指令 PWM**，而且是**经过 slew 之后**的值，**不是轮子实测转速**。日志里没有编码器/转速反馈。所以无法出现"我命令了 X、轮子只做到 Y"这种直接对比——**看不到执行端的真实响应**，也就无法直接坐实"电机反应慢"。

### 2. 能做的只是间接推断，且拆不干净
唯一可用的间接办法：看"**指令发生明显变化 → 传感器 pattern 开始往回走**"之间的时间差，作为**整个回路总延迟的上界**。但这个延迟里混了：

```
传感器采样 + 计算 + 电机响应 + 车体转动惯量(车要物理转过来)
```

**电机/轮子只是其中一环，从 log 里无法把它单独拆出来**——pattern 回中心慢，既可能是电机换向慢，也可能是车身惯量大要时间转，二者在 log 里长得一模一样。好处是：既然本次 `slew=5000` 已经把软件延迟基本去掉，这个"指令→pattern"的残余延迟主要就是"电机响应 + 车体动力学"之和，可作为**机械环节总延迟的粗略上界**。

### 3. log15 里疑似机械/惯量的痕迹（谨慎看待，非唯一解释）
- **换向/大修正后 pattern 不立刻回中**：如行 26 起进入 mode3 硬左（`pwm_l→-11`），但行 27–33 pattern 在 `00`(LOST)/`20`(CH6) 之间反复 dither、线没有果断拉回中心。可能是"响应跟不上"，也可能只是线正好停在 CH6 边界、传感器在阈值附近抖动——**证据不唯一**。
- **切换瞬间的 L/R 是 slew 半途值**：如行 47 `20 3 98 58`，mode3 本应压左轮，日志却显示右轮 58，这是上一状态的 slew 残值还没爬回，属**软件瞬态**，不能当成机械证据。
- 这些痕迹**都不足以单独证明**"电机轮子反应慢"，只能说"总回路还有一点残余滞后"。

### 4. 要真正判定电机/轮子这一环，必须直接测
- **加编码器 + 打时间戳**（最佳）：把编码器实测转速/计数也写进 log 行，就能直接对比"指令 PWM vs 实际转速"，那才是 log 里的**机械延迟直接证据**。当前固件没有这一路反馈，是加不出来的。
- **240fps 高速摄像做阶跃/换向测试**：停止→给 base、前进→反转，数帧算延迟 ms 数（见 `如何判断当前有没有机械延迟.md` 实验 C）。这是当前无编码器时唯一能实锤的手段。

### 5. 一句话
**现有 log 只能给"总回路延迟"的上界，无法单独证明电机/轮子慢；要坐实这一环，得给固件加编码器转速反馈，或用高速摄像直接量。** 而 log15 已经侧面说明：软件延迟才是之前的主因，机械延迟即便存在也不是当前主要瓶颈。

## 八、详解：为什么说"软件延迟(slew)才是之前的主因"

### 1. 这里的"软件延迟"具体指什么
指 `slew_rate` 这个 PWM 限速机制。代码里下发给电机的 PWM 不是想给多少就立刻给多少，而是**每秒最多变化 `slew_rate` 个单位**（`slew_toward()`）。当初加它是为了压 bang-bang 硬跳变导致的抖动。但它的副作用是：**任何一次修正指令，都要先花一段时间"爬"到目标值，电机才真正收到新指令**——这就是一段纯软件造成的执行滞后，发生在电机之前。

### 2. slew=600 到底加了多少延迟（可精确计算）
延迟 = 需要变化的 PWM 量 ÷ slew_rate。以最典型的"从直行切到内轮反转"为例，PWM 要从 base≈108 变到 ≈-20，跨度约 128 单位：

| slew_rate | 从 108 爬到 -20 需要 | 说明 |
|---|---|---|
| **600**（log13/14） | 128 ÷ 600 ≈ **213 ms** | 电机要 200ms 后才拿到完整的反转指令 |
| **5000**（log15） | 128 ÷ 5000 ≈ **26 ms** | 缩到约 1/8 |

**在一个巡线控制回路里，凭空多出 ~200ms 的执行滞后是致命的。** 这不是估计，是按公式算死的确定值——软件延迟**确定存在、且可精确量化**。

### 3. 它如何直接造成"往外扭"
回路里多 200ms 滞后 = 严重相位滞后。表现为两个方向都出问题：
- **小修正跟不上漂移**：线漂到 CH6 需要内轮减速，但 PWM 还在慢慢爬，几十毫秒内几乎没减速，线就溜出边缘丢线了。
- **大反转退不回来**：丢线时内轮猛冲到反转值，等找回线要恢复直行，PWM 又要花 ~200ms 才爬回来——**"已经找回线了、轮子却还在按旧指令猛掰"**，于是冲过头，形成左右发散的极限环。

### 4. log14 里的直接证据
log14（slew=600）行 45–47，mode3 的目标内轮 = base×0.35 ≈ **37**，但实测：

```
行45 pwm_l=107 → 行46 =98 → 行47 =91   （26ms 只从108降到91）
```

到目标 37 需要约 118ms，可线在边缘只停留几十毫秒。**内轮还卡在 ~100 没真正减速，车几乎还在直行，线就丢了**——这段迟钝完全是 slew 造成的，与电机无关。

### 5. 放开到 5000 后问题基本消失（log15）
同样的车、同样的机械，只把 slew 提到 5000（执行滞后从 ~200ms 缩到 ~26ms），直线就从"漂出去丢线"变成"3 秒干净直行 + 有界蛇形不丢线"。**改的是软件参数，机械一点没动，结果却根本性好转 → 主因在软件。**

### 6. 诚实说明一个混杂因素，以及为什么仍判定 slew 是主因
log14→log15 除了 slew，还同时软化了 `medium_ratio`(0.35→0.65) 和 `sharp_ratio`(-0.40→-0.20)，**不是严格的单变量实验**。但仍可判定 slew 是主因：
- 软化 ratio 只是**减小修正幅度**，对"修正跟不上漂移"这个滞后问题**没有帮助、甚至更弱**（修正更轻了）。既然在修正更轻的情况下反而不丢线了，说明起决定作用的是**把 slew 这段执行滞后去掉**，让修正能及时到位。
- slew 造成的延迟是**可按公式算死的确定量**（第 2 节），而 ratio 软化只影响幅度不影响滞后。因果链清晰。

### 7. 和"机械延迟"的区别（为什么先归因软件）
- **软件延迟(slew)**：已知机制、可精确计算(~200ms)、改个参数就能验证——这次一验就好了。
- **机械延迟**：未知量、log 里测不出来（无转速反馈，见第七节）、要靠编码器或高速摄像才能实锤。
- 排查顺序应"先易后难、先可算后未知"：既然去掉那段**可算的软件延迟**后问题基本消失，就没必要再把锅归到尚未测量的机械环节。机械延迟即便存在，也已不是当前主要瓶颈。

### 8. 小结
之前"往外扭/丢线"的主因，是 `slew_rate=600` 在电机之前凭空加了约 200ms 的**软件执行滞后**，造成回路相位滞后、修正既跟不上又退不回。把 slew 放开到 5000（滞后≈26ms）后问题基本消失，且机械未做任何改动，故判定**软件延迟为主因，机械延迟非当前瓶颈**。
