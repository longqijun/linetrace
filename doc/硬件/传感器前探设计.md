# 传感器前探设计

> 背景：弯道（尤其发卡）总是"冲到边缘才反应→过冲→丢线→盲目找线甩飞"（见 `log分析/log17分析.md`~`log20分析.md`）。前探（把传感器往车头前移）是缓解手段之一，但会带来一个真实的困惑：**前探后弯道里传感器数据可能更"乱"，甚至显示"冲出去/丢线"，可轮子明明还在轨道上——那到底怎么判断下一步动作？** 本文讲清这个矛盾和解法。

## 一、核心认知：前探的读数是"弯道预告"，不是"当前位置"

| | 贴轮子的传感器 | 前探的传感器 |
|---|---|---|
| 读数含义 | 车身**当前**横向偏差 | **前方那个点**轨道的位置（预测/前馈） |
| "线到边缘"意味着 | 车身已偏到边=快掉下去，紧急纠偏 | **前面有弯，该开始转了**（不是车要飞） |

**关键**：前探之后**不能再用"线到边=紧急纠偏/车要飞"这套逻辑读数据**。弯道里前方轨道本就往内侧拐，"线扫到边"多半是"弯道预告"。若仍按老逻辑解读，就会出现"数据看着像冲出去了、其实只是前面有弯"的误判——这正是困惑的来源。

## 二、"轮子在轨道上、传感器却显示丢线/冲出"——真实存在，但有条件

当**前探距离相对弯道半径太长**时：轨道拐得比整排传感器能覆盖的还快，线直接**跑出阵列视野（全黑=LOST）**，可轮子还在弯里好好走。

所以前探有个**甜区（sweet spot）**：
- **太短** → 没有预读价值，反应还是晚（和贴轮子差不多）。
- **太长** → 最紧的发卡时线跑出阵列，读数一片乱/丢线，反而更糟——就是上面这个现象。

```
        [前探太长]                    [前探合适]
   传感器 ●······?(线已拐出视野)   传感器 ●--线还在最外档
          |  弯                          | 弯
   轮子 ▮▮ 还在线上                轮子 ▮▮ 在线上
   → 读数=LOST，误判"飞了"         → 读数=HAIRPIN，正确"该猛转"
```

## 三、解法

### 方案 A：前探距离匹配最紧的弯（单排，最省）
- 规则：前探量要小到"跑**你最紧的发卡**时，线仍落在这排传感器宽度内"。发卡越紧，前探越要短（轮轴前几 cm）。
- 效果：弯来了线会扫到边缘档（SHARP/HAIRPIN）但**不会完全丢**，正好提前触发转向。
- 局限：探得少 → 预读时间也少。是"够用但不激进"的选择。

### 方案 B：双排传感器（最推荐，直接消除困惑）
- **贴轮子一排**：管"真实位置"，永远告诉你车身现在在哪、有没有真丢线。
- **前方一排**：管"预判"，看到弯提前给前馈。
- 融合：**近排定纠偏量（不会误判"飞出去"），远排定要不要提前加大转向/降速**。
- **为什么根治困惑**：即使"前排看着像冲出去"，**近排会告诉你轮子其实还在线上** → 你就知道那是"弯道预告"而非"真丢线"。竞速/电脑鼠常用此法。
- 代价：多一排传感器 + ADC 通道 + 代码要区分两排用途。

### 方案 C：加宽 / 带角度的阵列
- 把阵列做宽一点或末端向内偏，扩大视野，让紧弯时线不易跑出边界。介于 A、B 之间。

### 方案 D：配套——改"丢线"的解读（软件，配合前探）
- 前探后，"前排丢线"应理解为"**弯太急、线拐到视野外，继续朝最后看到的方向温和地转**"，而不是原地大幅反转找线（那正是当前每次甩飞的直接原因）。
- 与现有 `LOST` 延续 `_last_dir` 思路一致，但要**温和续转、别猛掰**，宁可短暂减速也别把车甩出赛道。

## 四、对当前发卡问题的实际结论

- 前探的价值：**更早看到发卡、更早开始掰**，减少"冲到边缘才反应"的过冲。
- 但你的发卡很紧：**单排前探不能探太远**，否则就是"线出视野一片乱"。要探得远又不丢线，就得上**双排**或**更宽/带角度阵列**。
- 现实建议：**要么前探一点点（保守单排），要么上双排。别单排探很远。**
- 注意：前探是"减少过冲"的辅助，不改变"车速降不下来"的根本墙（见 `如何判断当前有没有机械延迟.md`、`log分析/log20分析.md`）。它和"治盲目找线""降死区/齿轮比"是并行的手段，不是替代。

## 五、一句话
前探的数据要当"**弯道预告**"读，不是"当前位置"读；"轮子在线上但数据像飞了"是**前探过长导致线出视野**，解法是**前探距离配最紧弯**，或**加一排贴轮子的传感器专管真实位置**（双排），再配合"温和续转"的找线逻辑。
