# 算法管理单元（Algorithm Profile Manager）设计

> 状态：**已实现（2026-08-09），待编译/实车验证**。开放问题的拍板决策见文末。
> 目标：不再只按"控制律类型(bangbang/pid)"存两套参数，而是提供一个**多条目的算法管理单元**——可以存多个**命名的算法条目**，每个条目 = `id + 名称 + 控制律 + 一整套参数`。哪怕都用 bangbang，也能有好几套调参（保守/激进/发卡专用…）随时切换、互不覆盖。
> 背景：上一版实现的 `AlgoProfile`（bangbang/pid 各一套，见 `../调试/软件问题解决.md`）只是雏形；本设计把它推广，**将取代那两槽方案**。

## 一、概念模型

把"算法"重新定义为一个**条目(entry)**，而不是一个固定的控制律：

```
算法条目 (AlgoEntry)
├─ id        : 算法ID，从0开始（稳定，不随删除变化）
├─ name      : 算法名称 algoname（如 "bb-保守" / "pid-快" / "bb-发卡"）
├─ base      : 用哪个控制律（BANGBANG / PID / 预留 STOPGO…）
└─ params    : 该条目的一整套参数（speed/slew + 该控制律的增益）
```

**算法管理单元**持有：
- 一个条目数组 `AlgoEntry[N]`（多个条目，可多个共用同一 base）；
- 当前**激活条目 id** `active_id`（决定"现在跑哪条算法、用哪套参数"）；
- 与条目**无关的共享项**：传感器标定（阈值/白黑参考）、file_log —— 这些是硬件级、两算法通用，不进条目。

**单一事实来源**：巡线运行时直接读"激活条目"的 base 和 params，不再另存一份镜像。调参命令改的就是激活条目本身，切换只是改 `active_id`。

## 二、数据结构（字段清单）

```c
#define ALGO_MAX        8    // 最多条目数（可调；影响RAM/flash）
#define ALGO_NAME_LEN   16   // 名称最长15字符+结束符

enum BaseAlgo {              // 控制律（代码路径），可扩展
  BASE_BANGBANG = 0,
  BASE_PID      = 1,
  // BASE_STOPGO = 2,       // 预留：停走式(见"停走式转向算法方案.md")
};

typedef struct {
  bool  used;                 // 槽位是否启用（支持删除留空）
  char  name[ALGO_NAME_LEN];  // algoname
  int   base;                 // BaseAlgo

  // ---- 参数集（各 base 用各自子集；用不到的字段随存，不影响别的 base）----
  int   speed;                // 共用：速度档
  float slew_rate;            // 共用：PWM 限速

  // BANGBANG 专用
  float turn_ratio;           // 急弯外轮比例
  float medium_ratio, sharp_ratio, xsharp_ratio;  // 各档内轮
  float medium_speed, sharp_speed, hairpin_speed;  // 方案A分档降速
  int   min_move_pwm;         // 外轮最小前进PWM

  // PID 专用
  float pid_kp, pid_ki, pid_kd;
} AlgoEntry;
```

- **id = 数组下标**（稳定）：删除某条只把 `used=false`，id 不复用给别人（除非新建时复用空槽——见开放问题）。
- 参数集用"并集"结构：一个 struct 装下所有 base 的字段，某 base 用不到的就闲置。**好处是切换 base、增删 base 时结构不变，代码简单**；代价是每条目多几十字节（可接受）。
- 未来加控制律（如停走式），只加 base 枚举值 + 它的专用字段即可，管理单元框架不动。

管理单元状态：
```c
static AlgoEntry _algos[ALGO_MAX];
static int       _active_id;      // 当前激活条目
```

## 三、默认条目（开机 / 无配置时）

- id 0：`{used, name="bb-default", base=BANGBANG, 全默认}`
- id 1：`{used, name="pid-default", base=PID, 全默认}`
- 其余槽 `used=false`。
- `active_id = 0`。

用户可在此基础上 `algonew` 增加更多条目。

## 四、命令接口

### 管理命令（新增）
| 命令 | 作用 |
|---|---|
| `algolist` | 列出所有已启用条目：id、name、base(BB/PID)、speed 等关键参数，激活项标 `*` |
| `algouse N` | 把激活条目切到 id N（加载并运行它的 base+params） |
| `algonew <BB\|PID> <name>` | 在第一个空槽新建条目（该 base 的默认参数 + 名称），返回新 id |
| `algocopy N <name>` | 复制条目 N 到新空槽（便于"在现有调参上派生一个变体"再微调） |
| `algoname N <name>` | 重命名条目 N |
| `algodel N` | 删除条目 N（不允许删激活项/最后一项） |

### 调参命令（沿用现有，作用对象=激活条目）
`speed / slewrate / turnspeed / mediumratio / sharpratio / xsharpratio / mediumspeed / sharpspeed / hairpinspeed / minpwm / pid kp|ki|kd` —— 全部**修改当前激活条目**的对应字段（不再是全局单份）。

### 旧命令兼容
- `algo 0` / `algo 1`：作为**过渡别名**，等价于"切到 id 0 / id 1"（默认的 bb/pid 条目）。文档标注推荐改用 `algouse`。
- `save` / `config`：见下节。

## 五、存储（config.json）

```json
{
  "active": 2,
  "file_log": true,
  "threshold": [1200,1100,...],
  "white_ref": [690,770,...],
  "black_ref": [2400,2300,...],
  "algos": [
    {"id":0,"name":"bb-default","base":0,"speed":17,"slew_rate":5000,
     "turn_ratio":0.65,"medium_ratio":0.65,"sharp_ratio":-0.2,"xsharp_ratio":-0.6,
     "medium_speed":0.85,"sharp_speed":0.7,"hairpin_speed":0.85,"min_move_pwm":70,
     "pid_kp":40,"pid_ki":0,"pid_kd":5},
    {"id":1,"name":"pid-default","base":1,"speed":17,"slew_rate":5000, ... },
    {"id":2,"name":"bb-发卡","base":0,"speed":14, ... }
  ]
}
```
- `save`：把整个管理单元（所有已启用条目 + active + 共享标定）落盘。
- `config`：打印上面结构，`algolist` 是它的精简版。
- **向后兼容**：加载时若没有 `"algos"` 数组、只有老的扁平键/或上一版的 `bb`/`pid` 对象，则据此重建 id0(bangbang)、id1(pid) 两条，保证旧配置不丢。
- **缓冲**：8 条 ×十几字段 + 3 个数组，JSON 约 1.5~2KB，`StaticJsonDocument` 需扩到 4096 或改 `DynamicJsonDocument`（实现时定）。

## 六、内存 / 兼容影响
- RAM：`AlgoEntry` 约 80~90 字节 × 8 ≈ 0.7KB 静态。可接受（ESP32）。
- 取代上一版 `AlgoProfile[2]`：`track_module` 的双槽档案改为 `_algos[ALGO_MAX]` + `active_id`；`profile_capture/apply` 不再需要（运行时直接读激活条目）。`config_module` 的读写改为遍历 `algos` 数组。
- PARAMS 日志行：仍打印**激活条目**的生效参数，另建议加一个 `algoid=N name=<...>` 字段，方便回看某趟 log 用的是哪条算法。

## 八、实现决策（本次已按此开发）
| 开放问题 | 决策 |
|---|---|
| 条目上限 ALGO_MAX | **8** |
| 名称长度 | **16 字节**（≈5 汉字） |
| id 复用 | 删除后**复用空槽**（新建填第一个空槽，id=槽下标） |
| base 事后改 | 暂不提供 `algobase`，用 `algonew`/`algocopy` 更清晰 |
| `algo 0/1` 旧命令 | **保留为别名** = 切到 id0(bb)/id1(pid) 默认条目 |
| 正在跑时切换 | **允许热切换**，切换即清 PID 历史 |
| 默认条目可删 | 不能删**激活条目**，也不能删**最后一个**可用条目 |

命令：`algolist / algouse N / algonew BB|PID <name> / algocopy N <name> / algoname N <name> / algodel N`（`algo 0/1` 保留别名）。
config.json 用 `{active, file_log, threshold[], white_ref[], black_ref[], algos:[{id,name,base,...params}]}`；向后兼容旧扁平/`bb`/`pid` 格式。PARAMS 日志行加了 `algoid=N`。
涉及文件：`sensor_debug/track_module.{h,cpp}`、`config_module.cpp`、`cmd_module.cpp`。

## 七、（原）待 review 的开放问题
1. **条目上限 `ALGO_MAX`**：8 够吗？（每条 ~85B，16 条也才 1.4KB）
2. **名称长度**：15 字符够吗？要不要支持中文（UTF-8 下 15 字节≈5 汉字）？
3. **id 稳定性 / 复用**：删除后该 id 空着不复用（id 永远稳定，但会有空洞）？还是新建时复用最小空槽（id 会被别的条目占用）？我倾向**复用空槽**（省槽位），但你若在意"id 不变"可选不复用。
4. **base 可否事后改**：要不要 `algobase N <BB|PID>` 允许把一条的控制律改掉（参数保留）？还是新建更清晰？
5. **`algo 0/1` 旧命令**：保留为别名，还是直接废弃改 `algouse`？
6. **切换时机**：`algouse` 若在 `track on`（正在跑）时执行，是立即热切换还是拒绝（要求先 stop）？建议正在跑时允许热切换但清 PID 历史。
7. **默认条目可否删**：id0/id1 允许删吗？建议至少保留一条不可删。
