# log-alg0-1.txt 分析报告

**背景**：这是按`log10分析.md`的建议、把`slewrate`从5000降到300之后的第一次实车测试。用户反馈"直接跑飞了"。

配置（`PARAMS`行）：`algo=BANGBANG speed=17 turn_ratio=0.65 medium_ratio=0.35 sharp_ratio=-0.40 xsharp_ratio=-0.60 slew_rate=300.0`——跟`log10`相比**只有`slew_rate`这一个参数变了**（5000→300），其余`turn_ratio`/`medium_ratio`/`sharp_ratio`/`xsharp_ratio`/`speed`全部相同，是一次很干净的单变量对照。

时间线：`TRACK_ON t=1053356` → `TRACK_OFF t=1072782`，`elapsed=19426ms`（约19.4秒）、`lines=101`。这19.4秒里**连续触发了3次`LOST_STOP`**（第46、53、101行），一次比log10（110秒才丢线一次）密集得多——слew降到300之后情况明显变差了，不是变好。

---

## 1. 核心发现：`slewrate`降过头了，从"没有平滑"变成"平滑得太慢、反而滞后放大摇摆"

先看第一次失控的完整轨迹（`TRACK_ON`到第一次`LOST_STOP`，约5.3秒）。把`modeCode`按时间顺序摘出来（对照第7行的编码表）：

```
t'≈0.67s  MEDIUM_L(3)
t'≈0.77s  SHARP_L(5)
t'≈0.89s  HAIRPIN_L(7)  ← 左侧打到最狠的一档
t'≈1.54s  SHARP_L(5)    ← 开始往回摆
t'≈1.75s  MEDIUM_L(3)
t'≈1.87s  LOST_L(A)
t'≈1.90s  RIGHT缓转(2)  ← 越过中心，开始往右偏
t'≈1.93s  CROSS(9)
t'≈1.97s  RIGHT缓转(2)
t'≈2.09s  MEDIUM_R(4)
t'≈2.13s  SHARP_R(6)
t'≈2.22s  HAIRPIN_R(8)  ← 右侧也打到最狠的一档
t'≈3.06s  SHARP_R(6)    ← 开始往回摆
t'≈3.30s  MEDIUM_R(4)
t'≈3.56s  RIGHT缓转(2)
t'≈3.60s  CROSS(9)
t'≈3.62s  RIGHT缓转(2)
t'≈3.71s  LOST_R(B)
t'≈3.79s  MEDIUM_L(3)   ← 再次越过中心，往左偏
t'≈3.80s  SHARP_L(5)
t'≈3.71s  HAIRPIN_L(7)
t'≈3.80s  LOST_L(A)
t'≈5.30s  LOST_STOP(C)  ← 彻底丢线停车
```

这是一个非常典型的**"从左发卡打到右发卡、再打回左发卡，幅度没有收敛反而越走越远，最后冲出传感器检测范围"**的发散振荡，跟`log10`里"相邻档位来回快速跳动、幅度大致稳定"的振荡完全不是一回事——`log10`是"抖得快但没往外冲"，这次是"每一次修正都比上一次冲得更远"，5.3秒内就彻底失控。

**根因是`slewrate=300`把响应拖得太慢**：算一下，`base`≈108（`speed=17`），从直行(`108`)平滑到发卡弯目标（`108×(-0.60)=-64.8`），PWM要变化约173个单位，按300单位/秒的限速，需要`173/300≈0.58秒`才能真正到位。也就是说，车压到发卡弯传感器之后，实际下发的转向力度要花将近**半秒**才能追上目标值——这半秒里车还在按之前（偏弱的）力度继续往外冲，等PWM终于追上来的时候，车已经偏出去更远了，需要的修正量比原来更大，于是下一次摆动的目标更极端，如此往复，越摆越大，最终冲出传感器范围丢线。

这跟`log10分析.md`诊断的问题（`slewrate=5000`＝几乎不平滑，档位切换时PWM硬跳变，导致车在边界附近快速来回蹭）是**同一个参数的两个极端各自导致的不同故障模式**：
- **太高（5000）**：没有平滑，边界附近硬跳变→高频小幅摇摆（`log10`）
- **太低（300）**：平滑过度、响应滞后半秒量级→修正跟不上车漂移的速度→越摆越大的发散振荡，5秒左右就彻底失控（这次`log-alg0-1`）

两头都不对，说明`slewrate`存在一个中间的"甜点区间"，不是"越低越平滑越好"。

## 2. 后两次LOST_STOP：同样的模式反复出现

第二次（第46~53行之间，`E680`+几步很快又回到`LOST_STOP`）和第三次（第57~101行）失控前的档位序列，跟第一次几乎是同一个模板：缓转→中转→急转→发卡（一侧打满）→往回摆→越过中心→另一侧同样打满→再往回→丢线。第三次甚至比第一次多摆了一轮（第57~101行，约17秒才最终丢线，中间有一段时间`RIGHT缓转`附近来回但没有像前两次那么快发散，说明车偶尔能维持住，但整体还是不稳定的）。三次失控形态高度一致，进一步印证是`slewrate`这一个参数的系统性问题，不是偶发的传感器噪声或者某一次巧合。

---

## 3. 下一步调参建议

1. **`slewrate`不要停在300，回调到中间区间**：建议先试`slewrate 600`（在这次的300和`log10`的5000之间取一个更接近项目历史默认值800的点），跑一趟对比这次的"是否还会打到发卡满档后继续发散"。如果600还是发散，说明问题不完全在slew，可能是差速比例（尤其`xsharp_ratio=-0.60`这种大幅反转）本身对当前车重/速度偏猛；如果600明显比300和5000都稳，就在600附近小范围微调（±100~200）找到不再发散也不明显抖动的区间。
2. **不要跳过800直接试**：项目文档里`slewrate`默认值一直是800，这次是从5000一路降到300，中间跳过了默认值区间。按"改一个参数、每次只调一小步"的原则，建议先回到800附近验证一次，而不是在300和5000之间再随便选一个新数字，这样能顺便验证"默认值800当初到底合不合适"这个历史遗留问题。
3. **如果中间区间还是会在发卡弯（HAIRPIN）附近发散**，可以单独怀疑`xsharp_ratio=-0.60`是不是对现在的车速（`speed=17`）来说反转力度太猛——本次三次失控都是先冲到发卡弯满档才开始发散，可以尝试把`xsharp_ratio`从60%降到45~50%试试，跟slew分开测（一次只改一个变量）。
4. 每次测试都用现在这套log机制记录、跟这份报告的时间线做同样的"档位序列摘录"比对，能很直接看出是"幅度收敛了"还是"还在发散"，比单看统计数字更直观。
